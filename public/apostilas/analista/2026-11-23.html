Orientação a Objetos II: abstração, classes abstratas, interfaces, composição e o C# do dia a dia (coleções, genéricos, strings, iteradores e concorrência)

Este capítulo aprofunda os conceitos de orientação a objetos que distinguem um projeto bem feito: quando usar classe abstrata ou interface, por que preferir composição a herança, como representar essas relações na UML e como o polimorfismo funciona em C# e em C++. Como as provas de C# misturam OO com recursos práticos da linguagem, a segunda metade cobre coleções, genéricos, strings, iteradores com yield, namespaces, palavras-chave e o bloco lock.

1. Revisão rápida dos pilares

As principais características do paradigma orientado a objetos são abstração, encapsulamento, herança e polimorfismo. Uma classe define o comportamento (métodos) e o estado possível (atributos) dos objetos que são suas instâncias. Não há relação obrigatória entre o número de atributos e o número de métodos de uma classe: uma classe pode ter muitos atributos e poucos métodos, ou o contrário.

Abstração é a capacidade de extrair dos elementos da realidade suas principais características, ignorando detalhes irrelevantes para o problema. Sobrecarga significa ter mais de uma implementação de um método com o mesmo nome (e parâmetros diferentes); sobrescrita, redefinir na subclasse um método herdado com a mesma assinatura. O polimorfismo permite que objetos de classes diferentes respondam de forma diferente à mesma mensagem.

Um ponto de projeto frequentemente cobrado: sistemas orientados a objetos tendem a ser mais fáceis de modificar do que os desenvolvidos com abordagens funcionais/estruturadas, porque os objetos encapsulam estado e comportamento, e mudanças ficam localizadas. Os objetos devem esconder sua representação interna e comunicar-se por interfaces bem definidas.

2. Classes abstratas

Uma classe abstrata representa um conceito genérico demais para ter instâncias próprias, mas que reúne o que é comum às suas subclasses.

public abstract class Documento
{
    public string Numero { get; }
    protected Documento(string numero) { Numero = numero; }   // construtor permitido

    public abstract decimal CalcularTaxa();                    // abstrato: sem corpo
    public virtual string Resumo() => $"Doc {Numero}";        // virtual: pode ser sobrescrito
    public void Arquivar() { /* comum a todos */ }             // concreto
}

public class Contrato : Documento
{
    public decimal Valor { get; set; }
    public Contrato(string n, decimal v) : base(n) { Valor = v; }
    public override decimal CalcularTaxa() => Valor * 0.01m;   // obrigatório implementar
}
  • Não pode ser instanciada com new, mas pode ser usada como tipo de variável (Documento d = new Contrato(...)).
  • Pode ter atributos, construtores, métodos concretos, virtuais e abstratos.
  • Um método abstract só pode existir em classe abstrata, não tem corpo e é implicitamente virtual.
  • Uma subclasse concreta deve sobrescrever todos os métodos abstratos; se não o fizer, também precisa ser abstrata.
  • Não pode ser sealed (seria contraditório: existe para ser herdada).

3. Interfaces

Uma interface é um contrato: define um conjunto de membros (métodos, propriedades, eventos, indexadores) que as classes que a implementam se comprometem a oferecer. Ela descreve o que fazer, não como. Por convenção, em C# o nome começa com I.

public interface IExportavel
{
    string Exportar();                // implicitamente public e abstrato
}
public interface IAssinavel
{
    void Assinar(string usuario);
    bool Assinado { get; }
}

public class Relatorio : Documento, IExportavel, IAssinavel   // 1 classe + N interfaces
{
    public Relatorio(string n) : base(n) { }
    public override decimal CalcularTaxa() => 0;
    public string Exportar() => "...";
    public void Assinar(string u) { Assinado = true; }
    public bool Assinado { get; private set; }
}

IExportavel e = new Relatorio("R1");   // polimorfismo por interface
Console.WriteLine(e.Exportar());
  • Uma classe C# herda de uma classe, mas pode implementar várias interfaces. Assim, interfaces suprem a ausência de herança múltipla de classes.
  • Interfaces não podem ser instanciadas, não têm construtores e não têm campos de instância.
  • Uma interface pode herdar de outras interfaces.
  • Desde o C# 8, interfaces podem ter implementações padrão de métodos (default interface methods) e membros estáticos; em Java, isso existe desde a versão 8 (default e static). Ainda assim, não guardam estado de instância.
  • Implementação explícita: string IExportavel.Exportar() { ... } só pode ser chamada por uma referência do tipo da interface; usada quando duas interfaces têm membros com o mesmo nome.

4. Polimorfismo em profundidade

Em C#, o polimorfismo de sobrescrita exige que o método da base seja virtual, abstract ou override, e que a derivada use override. A chamada é resolvida pelo tipo do objeto em tempo de execução (despacho dinâmico, via tabela de métodos virtuais). Sem virtual, a chamada é resolvida pelo tipo da referência em tempo de compilação; com new na derivada, o método apenas oculta o da base.

O polimorfismo também ocorre por interfaces (várias classes sem parentesco implementando o mesmo contrato) e por genéricos (polimorfismo paramétrico: List<T> funciona para qualquer T).

Em C++

  • Classes derivadas são criadas com class Gerente : public Funcionario. C++ admite herança múltipla (com o "problema do diamante", resolvido com herança virtual).
  • Para haver ligação dinâmica, o método da base precisa ser declarado virtual, e a chamada deve ser feita por ponteiro ou referência à base. Uma função virtual pura (virtual double area() = 0;) torna a classe abstrata.
  • O ponteiro this é um ponteiro implícito, disponível nas funções-membro não estáticas, que aponta para o objeto que invocou a função.
  • C++ tem destrutores (~Classe()), chamados quando o objeto sai de escopo ou é deletado; em hierarquias, o destrutor da base deve ser virtual. Há também funções e classes friend, que acessam membros privados, e sobrecarga de operadores.

Composição × herança

A recomendação clássica (Gang of Four) é "favoreça a composição de objetos em vez da herança de classes". Motivos:

  • Herança é acoplamento forte e estático: a subclasse depende dos detalhes da superclasse, e mudanças na base podem quebrar as derivadas (classe base frágil). A relação é definida em tempo de compilação.
  • Composição é mais flexível: o objeto delega parte do trabalho a outro objeto, que pode ser trocado em tempo de execução, especialmente se for referenciado por uma interface. Favorece o encapsulamento ("caixa-preta").
  • Herança só é adequada quando a relação "é um" é verdadeira e estável e quando a subclasse pode substituir a superclasse sem quebrar o comportamento esperado (princípio de substituição de Liskov).
// Herança forçada: um Carro "é um" Motor? Não.
// Composição: um Carro "tem um" motor, que pode ser trocado.
public interface IMotor { void Ligar(); }
public class MotorEletrico : IMotor { public void Ligar() => Console.WriteLine("silencioso"); }
public class MotorFlex     : IMotor { public void Ligar() => Console.WriteLine("vrum"); }

public class Carro
{
    private readonly IMotor motor;                 // composição + dependência de abstração
    public Carro(IMotor motor) { this.motor = motor; }
    public void Partir() => motor.Ligar();         // delegação
}
new Carro(new MotorEletrico()).Partir();

6. Genéricos e coleções

Genéricos permitem escrever classes e métodos parametrizados por tipo, com segurança de tipo em tempo de compilação e sem conversões (boxing) desnecessárias: List<int>, Dictionary<string, Cliente>. Restrições de tipo usam a palavra contextual where: class Repositorio<T> where T : class, new().

As coleções não genéricas do namespace System.Collections (ArrayList, Hashtable) armazenam object e são consideradas legadas. ArrayList.AddRange também adiciona os elementos da coleção recebida no final da lista; para inserir em outra posição, usa-se InsertRange.

Coleções implementam IEnumerable<T>, o que permite percorrê-las com foreach e consultá-las com LINQ: lista.Where(x => x > 5).OrderBy(x => x).ToList().

7. Iteradores e yield return

Um método que devolve IEnumerable<T> pode usar yield return para produzir os valores um a um, sob demanda (execução adiada). A cada iteração do foreach, o método continua de onde parou. yield break encerra a sequência.

static IEnumerable<int> Multiplos(int limite, int passo)
{
    for (int i = 0; i <= limite; i += passo)
        yield return i;
}
foreach (int n in Multiplos(9, 3)) Console.Write(n + " ");   // 0 3 6 9

Rastreie como um laço comum: cada yield return entrega um valor ao foreach. Com limite 9 e passo 3: 0, 3, 6, 9 (o 12 já não satisfaz a condição).

9. Namespaces, nomes e palavras-chave

Um namespace organiza tipos e evita conflitos de nomes. Quando um nome local esconde um namespace ou tipo (por exemplo, uma classe com métodos chamados System() e Console()), referências como Console.WriteLine passam a ser interpretadas como o membro local e o código não compila. A solução é qualificar a partir da raiz com o alias global::: global::System.Console.WriteLine("ok");. Também é possível criar aliases: using Io = System.IO;.

As palavras reservadas (como class, int, if, new, this, base, static, virtual, override, abstract, sealed, lock, namespace, using) não podem ser usadas como identificadores (a menos que prefixadas com @, como @class). As palavras-chave contextuais só têm sentido especial em certos contextos e podem ser identificadores em outros: var, where, select, from, yield, async, await, get, set, value, partial, dynamic, nameof, record, init.

Classes aninhadas e modificadores

Classes de nível superior (diretamente no namespace) só podem ser public ou internal (o padrão). Uma classe private só é possível quando aninhada dentro de outra classe, e então só é acessível dentro da classe que a contém. Membros aninhados são private por padrão.

Mais detalhes de tipos que caem junto

  • Tipos inteiros sem sinal em C#: byte, ushort, uint, ulong (e nuint). Com sinal: sbyte, short, int, long. O int tem 4 bytes.
  • Conversões implícitas vão do menor para o maior sem perda: byte → int → long → double. De double para int, só com cast.
  • C# é de tipagem estática: em var num = 100; num = "teste";, a segunda linha não compila (num é int).
  • ++x-- não compila: o resultado de ++x é um valor, e não uma variável, então não pode receber outro incremento ou decremento. O mesmo vale para (x++)++ e 5++.
  • Precedência em expressões: 10 * 3 / 6 + 2 * 2 = 30 / 6 + 4 = 5 + 4 = 9 (multiplicação e divisão da esquerda para a direita, antes da soma). 4 * 5 + 9 % 4 = 20 + 1 = 21.

10. Concorrência: lock e condição de corrida

Quando várias threads acessam e alteram o mesmo dado ao mesmo tempo, o resultado pode depender da ordem imprevisível de execução: é a condição de corrida (race condition). Exemplo: duas threads fazem saldo += 100 simultaneamente; ambas leem o mesmo valor antigo e uma das somas se perde.

O bloco lock garante exclusão mútua: apenas uma thread por vez executa o trecho protegido (a seção crítica), evitando a condição de corrida.

private readonly object trava = new object();
public void Depositar(decimal v)
{
    lock (trava)           // só uma thread entra por vez
    {
        saldo += v;
    }
}

O objeto usado no lock deve ser um tipo de referência privado e dedicado (não use this, strings ou tipos públicos). lock é um atalho para Monitor.Enter/Monitor.Exit com try/finally. Excesso de bloqueios pode causar deadlock (duas threads esperando, cada uma, um recurso que a outra segura) e perda de desempenho. Outras ferramentas: Interlocked, SemaphoreSlim, coleções concorrentes (ConcurrentDictionary).

11. Código gerenciado

No .NET, o código gerenciado (managed code) é executado pelo CLR, que fica responsável pelo gerenciamento de memória (alocação e coleta de lixo), pela segurança de tipos e pelo tratamento de exceções. O código não gerenciado (por exemplo, C++ nativo chamado via interop) faz o próprio gerenciamento. Em C#, blocos unsafe permitem ponteiros, desde que o projeto seja compilado com essa opção.
