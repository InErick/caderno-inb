1. Exceções no projeto orientado a objetos

1.1 Conceito e fluxo

Uma exceção é um objeto que representa uma condição anormal ocorrida durante a execução. Quando um método encontra um erro que não sabe tratar, ele lança (throw) a exceção; o runtime então interrompe o fluxo normal e procura, subindo pela pilha de chamadas, um bloco catch compatível. Se nenhum for encontrado, o programa termina. Para que uma exceção seja capturada, o comando que a dispara precisa ter sido executado dentro de um bloco try (direta ou indiretamente, por um método chamado a partir dele).

static void Main()
{
    try
    {
        Processar("dados.csv");
    }
    catch (FileNotFoundException e)       // específica primeiro
    {
        Console.WriteLine("Arquivo não encontrado: " + e.FileName);
    }
    catch (IOException e)                 // mais geral (FileNotFoundException herda dela)
    {
        Console.WriteLine("Erro de E/S: " + e.Message);
    }
    finally
    {
        Console.WriteLine("fim");         // sempre executa
    }
}
static void Processar(string caminho)
{
    var linhas = File.ReadAllLines(caminho);   // pode lançar; não há try aqui,
}                                             // então a exceção sobe para o Main

1.2 Hierarquia de exceções

Em C#, todas as exceções derivam de System.Exception. A biblioteca as organiza em hierarquias: SystemException (lançadas pelo runtime, como NullReferenceException, IndexOutOfRangeException, InvalidCastException, ArithmeticException → DivideByZeroException e OverflowException), ArgumentException (→ ArgumentNullException, ArgumentOutOfRangeException), InvalidOperationException, IOException (→ FileNotFoundException, DirectoryNotFoundException); todas essas também derivam de SystemException. Como um catch captura a classe indicada e todas as suas subclasses, a ordem dos blocos deve ir do mais específico ao mais geral; o inverso é erro de compilação em C#.

1.3 Exceções personalizadas

public class SaldoInsuficienteException : Exception
{
    public decimal Faltante { get; }
    public SaldoInsuficienteException(decimal faltante)
        : base($"Saldo insuficiente. Faltam {faltante:C}.")
    {
        Faltante = faltante;
    }
}

public void Sacar(decimal valor)
{
    if (valor > saldo) throw new SaldoInsuficienteException(valor - saldo);
    saldo -= valor;
}

Convenções: o nome termina em Exception, a classe herda de Exception (ou de uma exceção mais específica), oferece construtores que repassam a mensagem e, quando encapsula outra, guarda-a em InnerException (throw new ErroDeNegocio("...", ex);).

1.5 Boas práticas

  • Use exceções para situações excepcionais, não para controle de fluxo comum (para validar entrada do usuário, prefira TryParse e testes).
  • Capture apenas o que você sabe tratar; não "engula" exceções com catch { } vazio.
  • Prefira exceções específicas a Exception genérica, tanto ao lançar quanto ao capturar.
  • Libere recursos em finally ou using.
  • Lance cedo (valide argumentos na entrada: ArgumentNullException.ThrowIfNull(x)) e capture tarde (no nível que pode decidir o que fazer).
  • Não exponha detalhes internos (stack trace, SQL) ao usuário final: registre em log e mostre mensagem amigável. Isso também é um controle de segurança de aplicações web.

2. Coesão e acoplamento

São as duas medidas clássicas de qualidade de um projeto modular:

  • Coesão: o grau em que os elementos de um módulo (os métodos e atributos de uma classe) trabalham juntos para uma única finalidade. Deseja-se alta coesão.
  • Acoplamento: o grau de dependência entre módulos. Deseja-se baixo acoplamento.
Tipos de coesão (da pior para a melhor)Tipos de acoplamento (do pior para o melhor)
coincidental (sem relação) → lógica (agrupados por categoria) → temporal (executados no mesmo momento) → procedural → comunicacional (mesmos dados) → sequencial (saída de um é entrada do outro) → funcional (tudo contribui para uma única função)de conteúdo (um módulo mexe nos dados internos do outro) → comum (dados globais compartilhados) → externo → de controle (passa flags que controlam a lógica do outro) → de carimbo (passa estruturas inteiras) → de dados (passa só os parâmetros necessários)

Alta coesão e baixo acoplamento tornam o sistema mais fácil de entender, testar, reutilizar e modificar: uma mudança fica localizada em poucos lugares. Os princípios SOLID e os padrões de projeto são, em grande parte, técnicas para chegar a esse resultado.

3. Princípios SOLID

Reunidos por Robert C. Martin, os cinco princípios orientam o projeto de classes:

S · Princípio da Responsabilidade Única (SRP)

"Uma classe deve ter um, e apenas um, motivo para mudar." Cada classe deve ter uma única responsabilidade (atender a um único ator ou interesse). Uma classe Funcionario que calcula salário, gera relatório em PDF e grava no banco tem três motivos para mudar (regras de RH, layout do relatório, banco de dados) e deve ser dividida. O SRP é a expressão de alta coesão.

O · Princípio Aberto/Fechado (OCP)

"Entidades de software devem estar abertas para extensão e fechadas para modificação" (Bertrand Meyer). Deve ser possível acrescentar comportamento novo sem alterar o código existente e testado, em geral por meio de abstrações e polimorfismo. Exemplo: em vez de um switch sobre o tipo de pagamento que precisa ser editado a cada novo meio, cria-se a interface IPagamento; um novo meio é uma nova classe.

L · Princípio da Substituição de Liskov (LSP)

"Objetos de uma subclasse devem poder substituir objetos da superclasse sem quebrar a corretude do programa" (Barbara Liskov). A subclasse deve honrar o contrato da base: não exigir pré-condições mais fortes, não entregar pós-condições mais fracas, não lançar exceções inesperadas. Uma classe Cachorro que sobrescreve EmitirSom() de Animal retornando "au-au" respeita o LSP. O exemplo clássico de violação é Quadrado herdando de Retangulo: definir a largura de um quadrado altera também a altura, quebrando o que um código que espera um retângulo assume. Outro sinal de violação: sobrescrever um método só para lançar NotImplementedException.

I · Princípio da Segregação de Interfaces (ISP)

"Clientes não devem ser forçados a depender de métodos que não usam." Prefira várias interfaces pequenas e específicas a uma interface "gorda". Uma interface IMultifuncional com Imprimir, Digitalizar e EnviarFax força uma impressora simples a implementar métodos vazios; o correto é separar em IImpressora, IScanner e IFax.

D · Princípio da Inversão de Dependência (DIP)

"Módulos de alto nível não devem depender de módulos de baixo nível; ambos devem depender de abstrações. Abstrações não devem depender de detalhes; detalhes devem depender de abstrações." Na prática, uma classe de regra de negócio depende de uma interface (IRepositorio, IExportador), e a implementação concreta é fornecida de fora, por injeção de dependência (normalmente pelo construtor).

// Violação do DIP: alto nível conhece as classes concretas
public class ServicoDeEnvio
{
    public void Enviar(string formato, Dados d)
    {
        if (formato == "xml") new ExportadorXml().Exportar(d);
        else if (formato == "json") new ExportadorJson().Exportar(d);
        else new ExportadorTexto().Exportar(d);
    }
}

// Respeitando o DIP (e o OCP): depende da abstração, que é injetada
public interface IExportador { void Exportar(Dados d); }
public class ServicoDeEnvio
{
    private readonly IExportador exportador;
    public ServicoDeEnvio(IExportador exportador) { this.exportador = exportador; }
    public void Enviar(Dados d) => exportador.Exportar(d);
}
DIP × injeção de dependência × inversão de controleO DIP é o princípio (dependa de abstrações). A injeção de dependência é uma técnica para aplicá-lo (as dependências são passadas de fora). A inversão de controle (IoC) é a ideia mais geral de que um framework ou contêiner, e não a própria classe, controla a criação e o fluxo.

Outros princípios citados com o SOLID

  • DRY (Don't Repeat Yourself): não duplicar conhecimento.
  • KISS (Keep It Simple) e YAGNI (You Aren't Gonna Need It): não construir o que não é necessário agora.
  • Lei de Deméter ("fale só com seus amigos próximos"): evitar cadeias como a.GetB().GetC().Fazer().
  • Características gerais da POO: encapsulamento, herança, polimorfismo, reutilização, modularidade e abordagem de baixo para cima (bottom-up: identificam-se os objetos e compõe-se o sistema a partir deles), ao contrário da programação estruturada, tipicamente de cima para baixo (top-down, decomposição funcional). Linguagens como C#, Java e Python oferecem encapsulamento, herança e polimorfismo.

4. Padrões de projeto (Design Patterns)

Um padrão de projeto é uma solução reutilizável e consagrada para um problema recorrente de projeto, descrita por nome, problema, solução e consequências. O livro Design Patterns (1994), da "Gangue dos Quatro" (GoF: Gamma, Helm, Johnson e Vlissides), catalogou 23 padrões em três categorias:

CategoriaPropósitoPadrões
Criacionaisabstrair o processo de criação de objetosAbstract Factory, Builder, Factory Method, Prototype, Singleton
Estruturaiscompor classes e objetos em estruturas maioresAdapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy
Comportamentaisdistribuir responsabilidades e organizar a comunicação entre objetosChain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor

{
    private static readonly Lazy<Configuracao> instancia = new(() => new Configuracao());
    private Configuracao() { }                    // construtor privado: ninguém mais cria
    public static Configuracao Instancia => instancia.Value;   // ponto global de acesso
}
public interface INotificacao { void Enviar(string msg); }
public class Email : INotificacao { public void Enviar(string m) { /* ... */ } }
public class Sms : INotificacao { public void Enviar(string m) { /* ... */ } }

public static class NotificacaoFactory            // fábrica: centraliza a decisão de qual classe criar
{
    public static INotificacao Criar(string tipo) => tipo switch
    {
        "email" => new Email(),
        "sms" => new Sms(),
        _ => throw new ArgumentException("tipo inválido")
    };
}

O exemplo acima é a "fábrica simples" (Simple Factory), muito cobrada simplesmente como padrão Factory. No Factory Method do GoF, a decisão fica num método sobrescrito por subclasses; no Abstract Factory, uma interface de fábrica tem vários métodos, um para cada produto da família, e cada fábrica concreta cria uma família inteira.

{
    private readonly List<IObservador> observadores = new();
    public void Inscrever(IObservador o) => observadores.Add(o);

    {

Strategy × State × Template MethodStrategy: o cliente escolhe o algoritmo, que é intercambiável (composição). State: o próprio objeto muda de comportamento conforme seu estado. Template Method: o esqueleto fica na superclasse e as subclasses preenchem passos (herança).

4.4 Padrões de arquitetura e do Java EE

  • MVC (Model-View-Controller): separa os dados e regras (Model), a apresentação (View) e o tratamento das requisições (Controller).
  • Front Controller: um ponto único de entrada (por exemplo, um Servlet) recebe todas as requisições HTTP e as direciona ao controlador adequado.
  • Facade (no contexto de EJB, Session Facade): fachada que expõe aos clientes uma interface simples para a lógica de negócio distribuída em vários componentes.
  • Outros: DAO (Data Access Object, isola o acesso a dados), DTO (objeto de transferência de dados), Repository, Dependency Injection.

5. Qualidade de software e tópicos vizinhos

Características de qualidade (ISO/IEC 25010)

Adequação funcional, eficiência de desempenho, compatibilidade, usabilidade, confiabilidade (maturidade, disponibilidade, tolerância a falhas, recuperabilidade), segurança, manutenibilidade (modularidade, reusabilidade, analisabilidade, modificabilidade, testabilidade) e portabilidade. A manutenibilidade é a característica ligada à facilidade de corrigir, adaptar e evoluir o código; a confiabilidade, à capacidade de funcionar sem falhas ao longo do tempo. (Esta é a lista da edição de 2011; a revisão de 2023 acrescentou safety e renomeou algumas características.)

Testes

  • Teste de regressão: reexecutar testes após uma alteração para verificar que a correção de um defeito (ou uma melhoria) não introduziu novos defeitos.
  • Níveis: unidade, integração, sistema e aceitação. Caixa-branca (estrutura interna) × caixa-preta (entradas e saídas). Exceções e casos de erro também devem ser testados.

Análise de Pontos de Função (APF)

Mede o tamanho funcional do software, independentemente da linguagem. Funções de dados: ALI (Arquivo Lógico Interno, mantido pela aplicação) e AIE (Arquivo de Interface Externa: grupo de dados logicamente relacionados, identificável pelo usuário, referenciado pela aplicação, mas mantido por outra aplicação). Funções de transação: entrada externa (EE), saída externa (SE) e consulta externa (CE).

Exercícios de fixação

Exercício 1

Considere:

try {
    Console.Write("A");
    int[] v = new int[2];
    v[2] = 10;
    Console.Write("B");
}
catch (IndexOutOfRangeException) { Console.Write("C"); }
catch (Exception) { Console.Write("D"); }
finally { Console.Write("E"); }
Console.Write("F");

A saída é:

  1. ABEF
  2. ACEF
  3. ACDEF
  4. ACE
  5. ADEF
Ver gabarito comentado

Gabarito: B. "A" é impresso; v[2] não existe (índices 0 e 1) e lança IndexOutOfRangeException, então "B" é pulado. Só o primeiro catch compatível executa ("C"), depois o finally ("E"), e o programa continua ("F").

Exercício 2

Sobre exceções em Java e em C#, é correto afirmar que:

  1. em C#, métodos devem declarar com throws as exceções que podem lançar;
  2. em Java, exceções verificadas devem ser capturadas ou declaradas na assinatura do método;
  3. em Java, RuntimeException é uma exceção verificada;
  4. em C#, a raiz da hierarquia é Throwable;
  5. em ambas, o bloco finally é obrigatório.
Ver gabarito comentado

Gabarito: B. C# não tem exceções verificadas nem throws na assinatura; RuntimeException é não verificada; Throwable é a raiz em Java; finally é opcional.

Exercício 3

Uma classe Pedido calcula impostos, formata o pedido em HTML para e-mail e o grava no banco de dados. O princípio SOLID mais diretamente violado é:

  1. responsabilidade única;
  2. substituição de Liskov;
  3. segregação de interfaces;
  4. aberto/fechado;
  5. inversão de dependência.
Ver gabarito comentado

Gabarito: A. Três responsabilidades, três motivos para mudar: baixa coesão.

Exercício 4

A classe AveVoadora tem o método Voar(). A subclasse Pinguim o sobrescreve lançando NotSupportedException, e um módulo que percorre uma lista de AveVoadora passa a falhar. O princípio violado é:

  1. responsabilidade única;
  2. substituição de Liskov;
  3. aberto/fechado;
  4. inversão de dependência;
  5. DRY.
Ver gabarito comentado

Gabarito: B. A subclasse não pode substituir a base sem quebrar o programa.

Exercício 5

Um módulo de relatórios precisa gerar arquivos em PDF, Excel e CSV, e novos formatos surgirão. Para acrescentar formatos sem alterar o código existente, deve-se aplicar principalmente:

  1. o princípio aberto/fechado, com uma abstração implementada por uma classe para cada formato;
  2. um switch central atualizado a cada formato;
  3. herança múltipla;
  4. o padrão Singleton;
  5. acoplamento de conteúdo.
Ver gabarito comentado

Gabarito: A. Extensão por novas classes, sem modificar as existentes. A alternativa B é exatamente o que o OCP evita.

Exercício 6

Um sistema deve garantir que exista uma única instância da classe que gerencia o arquivo de log, acessível de qualquer ponto da aplicação. O padrão adequado é:

  1. Prototype;
  2. Singleton;
  3. Builder;
  4. Facade;
  5. Observer.
Ver gabarito comentado
