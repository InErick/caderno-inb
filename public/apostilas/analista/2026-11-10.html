Processo de software e modelos de desenvolvimento

Hoje você vai entender como um software é construído, do pedido do cliente até a manutenção, e conhecer os modelos de processo que a FGV mais cobra: cascata, incremental, prototipação, espiral e Processo Unificado (RUP/UP).

1. O que é um processo de software

Um processo de software é o conjunto organizado de atividades que leva à produção de um software. Não importa o modelo escolhido: todo processo passa, de algum jeito, por quatro atividades fundamentais, segundo Sommerville.

  1. Especificação: definir o que o sistema deve fazer e suas restrições (os requisitos).
  2. Projeto e implementação: desenhar a solução e escrever o código.
  3. Validação: conferir se o sistema faz o que o cliente precisa (testes, revisões).
  4. Evolução: alterar o sistema ao longo do tempo para acompanhar novas necessidades.

Pressman descreve as mesmas ideias com outros nomes, as atividades metodológicas genéricas: comunicação, planejamento, modelagem, construção e entrega (implantação). Decore as duas listas: a FGV costuma trocar uma atividade de lugar ou incluir uma que não existe.

O ciclo de vida é a história completa do software: nasce de uma necessidade, é desenvolvido, entra em operação, sofre manutenções e, um dia, é desativado. O modelo de processo é a "receita" de como organizar as atividades dentro desse ciclo: em sequência, em pedaços, em voltas etc.

Para fixarProcesso = o que se faz (especificar, construir, validar, evoluir). Modelo de processo = em que ordem e de que forma isso é organizado.

2. Modelo em cascata (sequencial linear)

É o modelo mais antigo, descrito por Winston Royce em 1970. As fases acontecem uma depois da outra, e uma fase só começa quando a anterior termina e é aprovada:

Requisitos → Projeto → Implementação → Testes → Implantação → Manutenção

ExemploUm órgão público precisa de um sistema para emitir uma certidão definida em lei, com regras que não vão mudar. Dá para levantar tudo no início, aprovar o documento de requisitos e seguir fase a fase. Esse é o cenário ideal para a cascata.
VantagensDesvantagens
Simples de entender e de gerenciarO cliente só vê o sistema funcionando no fim
Documentação completa em cada faseMudança de requisito no meio do caminho custa caro
Funciona bem quando os requisitos são estáveis e bem conhecidosErros de requisito só aparecem tarde, nos testes

Uma variação muito cobrada é o modelo em V: é uma cascata em que cada fase de construção tem uma fase de teste correspondente. Requisitos ↔ teste de aceitação; projeto de arquitetura ↔ teste de integração; projeto detalhado ↔ teste de unidade.

PegadinhaCascata não é iterativa nem incremental. Se a alternativa disser que a cascata "permite entregas parciais frequentes" ou "acomoda bem mudanças de requisitos", está errada.

3. Modelo incremental

O sistema é dividido em incrementos. Cada incremento passa por análise, projeto, código e teste, e é entregue ao cliente como uma versão operacional. O primeiro incremento costuma ser o núcleo do produto: as funções essenciais. Os próximos acrescentam funcionalidades.

ExemploUm app de controle de gastos: o incremento 1 entrega cadastro de despesas e saldo do mês; o incremento 2, os gráficos; o incremento 3, a exportação para Excel. Desde o primeiro mês o usuário já usa o app de verdade.
  • Vantagens: o cliente recebe valor cedo; o feedback é mais rápido; é mais fácil testar partes menores; o risco de "falha total" diminui.
  • Desvantagens: exige uma boa arquitetura desde o início, para os incrementos se encaixarem; pode ser difícil definir o que entra em cada incremento.
Iterativo × incrementalIncremental = construir em pedaços, e cada pedaço novo soma funcionalidades. Iterativo = construir em ciclos de refinamento, refazendo e melhorando o que já existe. Os modelos modernos (RUP, ágeis) são os dois ao mesmo tempo: iterativos e incrementais.

4. Prototipação

Constrói-se rapidamente um protótipo, uma versão simplificada (telas, fluxo), para o cliente experimentar. O objetivo principal é esclarecer requisitos quando o cliente não sabe explicar exatamente o que quer.

Ciclo típico: comunicação → plano rápido → modelagem rápida → construção do protótipo → avaliação pelo cliente → ajuste → repete.

  • Protótipo descartável: serve só para aprender e depois é jogado fora; o sistema real é feito do zero.
  • Protótipo evolutivo: é refinado aos poucos até virar o produto final.
Risco clássicoO cliente vê o protótipo funcionando e acha que o sistema "já está quase pronto", pressionando para colocar em produção algo que foi feito às pressas, sem qualidade.

5. Modelo espiral (Boehm)

Proposto por Barry Boehm, é um modelo evolucionário que junta a natureza iterativa da prototipação com o controle sistemático da cascata. A grande marca do espiral é a análise de riscos em cada volta.

Cada volta da espiral passa por quatro setores (versão de Sommerville):

  1. Definição de objetivos: metas e restrições da etapa.
  2. Avaliação e redução de riscos: identificar o que pode dar errado e agir (por exemplo, fazendo um protótipo).
  3. Desenvolvimento e validação: escolher o modelo de desenvolvimento para aquela volta e construir.
  4. Planejamento: revisar com o cliente e planejar a próxima volta.

Cada volta representa uma fase do processo. As primeiras voltas podem gerar só um conceito ou protótipo; as últimas, versões cada vez mais completas.

Na prova"Falou em risco, pense em espiral." Ele é indicado para projetos grandes, caros e com muita incerteza. Desvantagem: depende de equipe experiente em análise de riscos e pode ficar caro para projetos pequenos.

6. Processo Unificado (UP / RUP)

O Processo Unificado (e sua versão comercial da IBM, o RUP) tem três características que caem muito:

  • Iterativo e incremental;
  • dirigido por casos de uso (os casos de uso guiam todo o desenvolvimento);
  • centrado na arquitetura (a arquitetura é definida e testada cedo).

Ele se organiza em 4 fases, cada uma com várias iterações e terminando em um marco:

FaseFocoMarco ao final
Concepção (iniciação)Visão do produto, escopo, viabilidade, principais riscosObjetivos do ciclo de vida
ElaboraçãoDetalhar requisitos e definir/validar a arquitetura; atacar os maiores riscosArquitetura do ciclo de vida
ConstruçãoDesenvolver a maior parte do código e testarCapacidade operacional inicial (versão beta)
TransiçãoEntregar ao usuário: implantação, treinamento, ajustesRelease do produto

Além das fases (dimensão do tempo), o RUP tem disciplinas (dimensão do conteúdo): modelagem de negócio, requisitos, análise e design, implementação, teste e implantação, mais as de apoio: gerência de configuração e mudança, gerência de projeto e ambiente. Todas as disciplinas acontecem em todas as fases, com intensidades diferentes.

MnemônicoC-E-C-T: "Começa, Estrutura, Constrói, Transfere". A arquitetura é o coração da Elaboração.

7. Modelos tradicionais × ágeis (visão geral)

Os modelos acima são chamados de prescritivos ou dirigidos a plano: tentam prever e planejar quase tudo antes. Os métodos ágeis (Scrum, XP, Kanban, que você verá em detalhe mais à frente) partem do contrário: aceitam que a mudança vai acontecer e trabalham em ciclos curtos, com entregas frequentes e muito contato com o cliente.

Tradicional (preditivo)Ágil (adaptativo)
PlanejamentoDetalhado no inícioContínuo, a cada ciclo
MudançasEvitadas, custam caroBem-vindas, mesmo tarde
EntregasNormalmente no fimFrequentes (semanas)
DocumentaçãoExtensaSuficiente
Indicado quandoRequisitos estáveis, contexto reguladoRequisitos incertos, mudam com frequência

Mapa-resumo

ModeloPalavra-chaveUse quando…
CascataSequencial, fase a faseRequisitos claros e estáveis
Modelo em VCada fase ↔ um tipo de testePrecisa de muita verificação
IncrementalEntregas operacionais em partesCliente quer valor cedo

Exercícios de fixação

Questões inéditas no estilo FGV, escritas para esta apostila. Resolva antes de abrir o gabarito.

Questão 1 · inédita

Uma equipe vai desenvolver um sistema para uma agência reguladora. O escopo é definido por uma resolução já publicada, e o cliente exige documentação aprovada ao fim de cada etapa. O modelo de processo mais adequado é o

  1. espiral, pela análise contínua de riscos.
  2. cascata, pela estabilidade dos requisitos e pela documentação por fase.
  3. prototipação descartável, para descobrir os requisitos.
  4. incremental, porque o cliente quer entregas parciais frequentes.
  5. Scrum, porque elimina a necessidade de documentação.
Ver gabarito comentado

Gabarito: B. Requisitos estáveis (definidos em norma) e exigência de documentação aprovada fase a fase são exatamente o cenário da cascata. A letra E também erra porque nenhum método ágil "elimina" documentação: ele busca a documentação suficiente.

Questão 2 · inédita

No modelo espiral, a atividade que mais o diferencia dos demais modelos de processo é

  1. a entrega de um incremento operacional a cada volta.
  2. a elaboração de casos de uso antes da arquitetura.
  3. a avaliação e redução de riscos em cada ciclo.
  4. a execução dos testes apenas ao final do projeto.
  5. a ausência de planejamento formal.
Ver gabarito comentado

Gabarito: C. A análise de riscos é a marca registrada do espiral. A letra A descreve o incremental; a D descreve a cascata.

Questão 3 · inédita

Sobre as fases do Processo Unificado, a fase cujo principal objetivo é definir e validar uma arquitetura executável, atacando os maiores riscos técnicos, é a

  1. Concepção.
  2. Elaboração.
  3. Construção.
  4. Transição.
  5. Implantação.
Ver gabarito comentado

Gabarito: B. A Elaboração termina com o marco "arquitetura do ciclo de vida". A letra E é uma disciplina do RUP, não uma fase.

Questão 4 · inédita

Um cliente diz: "Não sei bem como deve ser a tela de agendamento, mas vou saber quando vir". A abordagem mais indicada para levantar os requisitos dessa funcionalidade é

  1. a prototipação.
  2. o modelo em V.
  3. a cascata pura.
  4. a fase de Transição do RUP.
  5. a manutenção corretiva.
Ver gabarito comentado

Gabarito: A. A prototipação existe justamente para quando o cliente tem dificuldade de explicar o que quer, mas reconhece o que serve ao experimentar.

Questão 5 · inédita

Analise as afirmativas sobre modelos de processo:
I. No modelo incremental, cada incremento entregue é uma versão operacional do produto.
II. O modelo cascata é iterativo, pois permite voltar livremente a fases anteriores.
III. O RUP é dirigido por casos de uso e centrado na arquitetura.
Está correto o que se afirma em

  1. I, apenas.
  2. II, apenas.
  3. I e III, apenas.
  4. II e III, apenas.
  5. I, II e III.
Ver gabarito comentado

Gabarito: C. II está errada: a cascata é sequencial, e voltar a uma fase anterior é exceção cara, não característica do modelo.

Questão 6 · inédita

No modelo em V, o teste de aceitação está associado à fase de

  1. codificação.
  2. projeto detalhado.
  3. projeto de arquitetura.
  4. especificação de requisitos.
  5. manutenção.
Ver gabarito comentado

Gabarito: D. O teste de aceitação confere se o sistema atende aos requisitos do usuário; por isso fica "espelhado" com a especificação de requisitos. Projeto de arquitetura ↔ integração; projeto detalhado ↔ unidade.

Questão 7 · inédita

Segundo Sommerville, as quatro atividades fundamentais de qualquer processo de software são

  1. comunicação, planejamento, modelagem e construção.
  2. especificação, projeto e implementação, validação e evolução.
  3. concepção, elaboração, construção e transição.
  4. requisitos, codificação, implantação e descarte.
  5. análise, testes, homologação e manutenção.
Ver gabarito comentado

Gabarito: B. A letra A traz atividades de Pressman (incompletas, falta a entrega); a C traz as fases do UP.

Questão 8 · inédita

Comparando abordagens tradicionais e ágeis, é correto afirmar que

  1. os métodos ágeis dispensam qualquer planejamento.
  2. as abordagens tradicionais tratam mudanças tardias de requisitos como algo natural e barato.
  3. os métodos ágeis trabalham com ciclos curtos e entregas frequentes de software funcionando.
  4. o modelo cascata é o mais indicado para requisitos instáveis.
  5. o modelo espiral é uma metodologia ágil.
Ver gabarito comentado

Gabarito: C. Ágil planeja o tempo todo (A errada); mudança tardia é cara no tradicional (B errada); cascata é para requisitos estáveis (D errada); espiral é um modelo evolucionário, não ágil (E errada).
