Requisitos I — levantamento, análise, especificação e validação

Engenharia de requisitos é um dos temas preferidos da FGV em provas de Analista de Sistemas. Hoje você aprende o processo completo, as técnicas de levantamento e, principalmente, a separar requisito funcional de não funcional, que é o tipo de questão que mais cai.

1. O que é um requisito

Um requisito é a descrição de algo que o sistema deve fazer ou de uma condição que ele deve respeitar. Ele nasce da necessidade de alguém: usuário, cliente, gestor, uma lei.

Sommerville separa dois níveis de detalhe:

  • Requisitos de usuário: escritos em linguagem natural, com diagramas simples, para o cliente entender. Ex.: "O sistema deve permitir que o servidor solicite férias."
  • Requisitos de sistema: versão detalhada e técnica, base para o projeto e o contrato. Ex.: "A solicitação de férias deve registrar matrícula, período (máximo de 3 frações) e enviar notificação ao chefe imediato."

Quem tem interesse no sistema é chamado de stakeholder (parte interessada): usuários finais, gestores, área jurídica, equipe de TI, órgãos de controle.

2. O processo de engenharia de requisitos

É um processo iterativo: as atividades se repetem e se realimentam, não acontecem uma única vez.

  1. Levantamento (elicitação): descobrir as necessidades junto aos stakeholders.
  2. Análise: organizar, classificar, priorizar e resolver conflitos entre requisitos.
  3. Especificação: documentar os requisitos de forma clara e padronizada.
  4. Validação: conferir com os stakeholders se os requisitos documentados são os que eles realmente querem.

Ao lado dessas atividades corre o gerenciamento de requisitos (controle de mudanças, rastreabilidade), que você estuda amanhã. Sommerville também cita o estudo de viabilidade no começo: vale a pena construir esse sistema?

3. Funcionais × não funcionais

Esta é a seção mais importante do dia.

Requisito funcional (RF)Requisito não funcional (RNF)
Diz o que o sistema faz: serviços, funções, reações a entradasDiz como o sistema deve ser: qualidades e restrições
"O sistema deve emitir o contracheque em PDF.""O contracheque deve ser gerado em até 3 segundos."
"O usuário deve poder redefinir a senha por e-mail.""As senhas devem ser armazenadas com hash e salt."
"O sistema deve permitir filtrar processos por data.""O sistema deve funcionar nos navegadores Chrome e Firefox."
Truque para a provaPergunte: "Isso é uma ação/função que o usuário pode pedir ao sistema?" Se sim, é RF. Se a frase fala de velocidade, segurança, disponibilidade, usabilidade, compatibilidade, lei, padrão, tecnologia, é RNF.

Classificação dos RNF (Sommerville)

  • Requisitos de produto: comportamento do software. Eficiência (desempenho, uso de memória), confiabilidade, proteção/segurança, usabilidade.
  • Requisitos organizacionais: vêm de políticas da organização. Ex.: "deve ser desenvolvido em C#/.NET", "deve usar o login único do órgão".
  • Requisitos externos: vêm de fora. Regulatórios, legais e éticos. Ex.: "deve cumprir a LGPD".

Há ainda os requisitos de domínio, que vêm do domínio de aplicação (área de negócio) e podem ser funcionais ou não funcionais. Ex.: num sistema bancário, "o cálculo de juros deve seguir a regra do Banco Central".

RNF bom é RNF mensurável

"O sistema deve ser rápido" é um requisito ruim: não dá para testar. A versão boa traz uma métrica:

Ruim → bom"Deve ser rápido" → "95% das consultas devem responder em até 2 segundos com 500 usuários simultâneos."
"Deve ser fácil de usar" → "Um usuário novo deve conseguir abrir um chamado em até 3 minutos, sem treinamento."
"Deve estar sempre no ar" → "Disponibilidade mínima de 99,5% no mês."

Qualidade de software: ISO/IEC 25010

A norma de qualidade de produto (versão de 2011, a mais cobrada) lista 8 características, ótimas para classificar RNF: adequação funcional, eficiência de desempenho, compatibilidade, usabilidade, confiabilidade, segurança, manutenibilidade e portabilidade.

4. Técnicas de levantamento

TécnicaComo funcionaBom para…
EntrevistaConversa com o stakeholder; pode ser fechada (perguntas prontas) ou aberta (livre)Entender o trabalho e as dores de cada pessoa
QuestionárioPerguntas enviadas a muitas pessoasPúblico grande e disperso
Workshop / JADSessão em grupo, com facilitador, usuários e TI juntosChegar a consenso rápido e resolver conflitos
BrainstormingGerar muitas ideias sem julgar, depois filtrarFuncionalidades novas, inovação
Observação / etnografiaO analista acompanha o trabalho real do usuárioDescobrir requisitos implícitos, que ninguém lembra de falar
PrototipaçãoMostrar telas/modelos para o usuário reagirInterfaces e requisitos incertos
Cenários e casos de usoDescrever interações passo a passoDetalhar fluxos e exceções

Por que levantar requisitos é difícilOs stakeholders muitas vezes não sabem o que querem, usam a linguagem da área deles, têm interesses em conflito, e os requisitos mudam durante o projeto. A FGV gosta de pedir a técnica certa para cada um desses problemas.

5. Especificação

O resultado é o documento de requisitos (também chamado SRS, especificação de requisitos de software). As normas de referência são a antiga IEEE 830 e a atual ISO/IEC/IEEE 29148. Características de um bom requisito:

  • Correto e necessário: representa uma necessidade real;
  • Não ambíguo: só uma interpretação possível;
  • Completo e consistente: não falta nada e nenhum requisito contradiz outro;
  • Verificável (testável): dá para provar que foi atendido;
  • Rastreável: dá para saber de onde veio e onde foi implementado;
  • Priorizado: indica importância ou urgência.
Ambíguo × claro"O sistema deve exibir os processos recentes." (recente quanto?)
→ "O sistema deve exibir os processos cadastrados nos últimos 30 dias, do mais novo para o mais antigo."

6. Validação

A validação verifica se o documento descreve o sistema que o cliente realmente quer. Erros de requisito descobertos tarde (em produção) custam muitas vezes mais do que se fossem achados aqui.

O que se confere: validade (é a necessidade certa?), consistência, completude, realismo (é possível fazer com o orçamento e a tecnologia?) e verificabilidade.

Técnicas: revisões e inspeções do documento, prototipação e geração de casos de teste (se não dá para escrever um teste, o requisito está mal escrito).

Verificação × validação (Boehm)Validação: "Estamos construindo o produto certo?" (atende ao cliente?)
Verificação: "Estamos construindo o produto certo da forma certa?" (está de acordo com a especificação?)

Mapa-resumo

  • Processo: levantamento → análise → especificação → validação, de forma iterativa, com gerenciamento ao lado.
  • RF = o que faz. RNF = como deve ser (qualidade e restrição), de produto, organizacional ou externo.
  • RNF precisa ser mensurável.
  • Técnica certa para cada problema: observação para o que ninguém fala; JAD para consenso; protótipo para incerteza; engenharia reversa para legado.
  • Bom requisito: não ambíguo, completo, consistente, verificável, rastreável.

Exercícios de fixação

Questões inéditas no estilo FGV, escritas para esta apostila.

Questão 1 · inédita

Em entrevista, a chefe do almoxarifado pediu: (1) cadastrar entradas de material; (2) "que a tela abra rápido, em menos de 2 segundos"; (3) emitir relatório mensal de consumo por setor; (4) "que funcione no celular dos conferentes"; (5) alertar quando o estoque ficar abaixo do mínimo. A quantidade de requisitos funcionais e não funcionais é, respectivamente,

  1. 2 e 3.
  2. 3 e 2.
  3. 4 e 1.
  4. 5 e 0.
  5. 1 e 4.
Ver gabarito comentado

Gabarito: B. Funcionais: cadastrar entradas (1), emitir relatório (3), alertar estoque mínimo (5). Não funcionais: desempenho (2) e compatibilidade/portabilidade (4).

Questão 2 · inédita

Uma equipe precisa substituir um sistema de folha de pagamento de 1998, sem documentação e cujos desenvolvedores já saíram do órgão. A técnica de levantamento mais adequada como ponto de partida é

  1. o brainstorming com os novos estagiários.
  2. o questionário enviado a todos os servidores.
  3. a engenharia reversa do sistema legado (código, banco de dados e telas).
  4. a prototipação descartável de novas telas.
  5. a especificação direta de casos de teste.
Ver gabarito comentado

Gabarito: C. Quando o conhecimento das regras está "preso" no sistema antigo, a engenharia reversa é a forma de recuperar os requisitos. As outras técnicas podem complementar depois.

Questão 3 · inédita

O requisito "O sistema deve estar em conformidade com a Lei Geral de Proteção de Dados" é classificado, segundo Sommerville, como requisito

  1. funcional de usuário.
  2. não funcional de produto.
  3. não funcional organizacional.
  4. não funcional externo.
  5. de domínio funcional.
Ver gabarito comentado

Gabarito: D. Requisitos legais e regulatórios vêm de fora da organização: são não funcionais externos.

Questão 4 · inédita

Assinale a opção que apresenta um requisito não funcional adequadamente especificado.

  1. O sistema deve ser intuitivo.
  2. O sistema deve ter ótimo desempenho.
  3. O sistema deve suportar 1.000 acessos simultâneos com tempo de resposta de até 3 segundos em 95% das requisições.
  4. O sistema deve permitir a emissão de boletos.
  5. O sistema deve ser seguro contra qualquer ataque.
Ver gabarito comentado

Gabarito: C. É o único mensurável e verificável. A, B e E são vagos; D é um requisito funcional.

Questão 5 · inédita

Os servidores de um setor sempre esquecem de mencionar, nas entrevistas, um controle paralelo que fazem numa planilha. A técnica mais indicada para revelar esse tipo de requisito implícito é

  1. a observação do trabalho (etnografia).
  2. a entrevista fechada.
  3. a análise de pontos de função.
  4. o modelo em V.
  5. a revisão por pares do código.
Ver gabarito comentado

Gabarito: A. Observando a rotina real, o analista vê o que as pessoas fazem e não lembram de contar.

Questão 6 · inédita

Durante a validação de requisitos, a equipe tentou escrever casos de teste para cada requisito e não conseguiu fazê-lo para "o sistema deve ser amigável". Isso indica que o requisito não atende principalmente à característica de

  1. rastreabilidade.
  2. verificabilidade.
  3. consistência.
  4. priorização.
  5. modularidade.
Ver gabarito comentado

Gabarito: B. Se não é possível testar, o requisito não é verificável. A geração de casos de teste é justamente uma técnica de validação.

Questão 7 · inédita

A pergunta "Estamos construindo o produto certo?" está associada à

  1. verificação.
  2. validação.
  3. implantação.
  4. manutenção adaptativa.
  5. gerência de configuração.
Ver gabarito comentado

Gabarito: B. Validação confere se o produto atende às necessidades reais do cliente. Verificação confere se o produto está de acordo com a especificação.

Questão 8 · inédita

Duas diretorias apresentam necessidades conflitantes para o mesmo módulo de um sistema. Para obter consenso rápido entre elas, com participação conjunta de usuários e equipe de TI, é mais indicado usar

  1. questionário anônimo.
  2. análise de documentos.
  3. workshop no formato JAD.
  4. engenharia reversa.
  5. observação passiva.
Ver gabarito comentado

Gabarito: C. O JAD (Joint Application Design) reúne todos numa sessão facilitada, ideal para negociar e fechar decisões.
