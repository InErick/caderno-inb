Requisitos I — levantamento, análise, especificação e validação

Engenharia de requisitos é um dos temas preferidos da FGV em provas de Analista de Sistemas. Hoje você vai estudar o processo completo, as tarefas de Pressman, a classificação detalhada dos requisitos não funcionais, as técnicas de levantamento com prós e contras, o que é uma boa especificação e como validar. A parte mais cobrada é separar requisito funcional de não funcional, e ela recebe atenção especial.

1. O que é um requisito

Segundo a definição clássica do IEEE, um requisito é uma condição ou capacidade de que um usuário precisa para resolver um problema ou alcançar um objetivo, ou que o sistema deve ter para satisfazer um contrato, padrão ou especificação. Em palavras simples: é a descrição de algo que o sistema deve fazer ou de uma condição que ele deve respeitar.

Os requisitos são a base de tudo o que vem depois: projeto, código, testes, contrato e prazo. Por isso, erros aqui são os mais caros, porque se espalham por todas as fases seguintes.

1.1 Requisitos de usuário × de sistema

Sommerville separa dois níveis de detalhe para o mesmo assunto:

Requisito de usuárioRequisito de sistema
Linguagem natural, com diagramas simples, para clientes e gestores entenderemDescrição detalhada e técnica do que o sistema faz; base para o projeto e, muitas vezes, para o contrato
"O sistema deve permitir que o servidor solicite férias.""A solicitação de férias deve registrar matrícula, período de até 3 frações, data de início não inferior a 30 dias da solicitação e enviar notificação por e-mail ao chefe imediato."

1.2 Stakeholders

Quem tem interesse no sistema é chamado de stakeholder (parte interessada). Não são só os usuários: gestores que pagam o projeto, a área jurídica, a equipe de TI que vai manter, órgãos de controle, até sistemas que vão se integrar. Esquecer um stakeholder importante é uma das causas mais comuns de requisitos faltando.

2. O processo de engenharia de requisitos

O processo é iterativo: as atividades se repetem e se realimentam ao longo do projeto, não acontecem uma única vez. Sommerville descreve as atividades principais:

  1. Estudo de viabilidade: vale a pena construir esse sistema? Ele contribui para os objetivos da organização, é possível com a tecnologia e o orçamento disponíveis?
  2. Elicitação (levantamento) e análise: descobrir as necessidades junto aos stakeholders. Inclui as subatividades de descoberta, classificação e organização, priorização e negociação e documentação.
  3. Especificação: documentar os requisitos de forma clara e padronizada.
  4. Validação: conferir com os stakeholders se os requisitos documentados são os que eles realmente querem.

Ao lado dessas atividades corre o gerenciamento de requisitos (controle de mudanças, rastreabilidade), que você estuda amanhã.

2.1 As sete tarefas de Pressman

Pressman detalha a engenharia de requisitos em sete tarefas, que a FGV também cobra:

TarefaO que acontece
ConcepçãoEntendimento básico do problema, de quem precisa da solução e da natureza da solução desejada
LevantamentoPerguntar aos interessados quais são os objetivos, o que precisam e como o sistema se encaixa no negócio
ElaboraçãoRefinar e expandir as informações em um modelo de requisitos (cenários, casos de uso, classes de análise)
NegociaçãoConciliar conflitos entre interessados e priorizar o que entra, com base em custo e risco
EspecificaçãoProduzir o documento ou modelo final (texto, cenários, modelos gráficos, protótipo)
ValidaçãoAvaliar a qualidade dos produtos: ambiguidades, omissões, inconsistências, requisitos irreais
GestãoAcompanhar e controlar as mudanças nos requisitos ao longo do projeto
Mnemônico"Com Lápis, Eu Nunca Erro Valores Grandes": Concepção, Levantamento, Elaboração, Negociação, Especificação, Validação, Gestão.

3. Por que levantar requisitos é difícil

Sommerville lista os problemas mais comuns, e a FGV gosta de pedir qual técnica resolve cada um:

  • Os stakeholders muitas vezes não sabem exatamente o que querem, ou pedem coisas impossíveis ou caras demais.
  • Eles expressam os requisitos na linguagem da área deles, com conhecimento implícito que o analista não tem.
  • Stakeholders diferentes têm requisitos conflitantes.
  • Fatores políticos influenciam os requisitos (um gestor quer um recurso para ganhar poder no setor).
  • O ambiente muda durante o projeto: novos stakeholders, novas leis, novas prioridades.

4. Funcionais × não funcionais

Esta é a seção mais importante do dia.

Requisito funcional (RF)Requisito não funcional (RNF)
Diz o que o sistema faz: serviços, funções, como reage a entradas e como se comporta em situações específicasDiz como o sistema deve ser: qualidades, restrições sobre os serviços e o processo de desenvolvimento
"O sistema deve emitir o contracheque em PDF.""O contracheque deve ser gerado em até 3 segundos."
"O usuário deve poder redefinir a senha por e-mail.""As senhas devem ser armazenadas com hash e salt."
"O sistema deve permitir filtrar processos por data.""O sistema deve funcionar nos navegadores Chrome e Firefox."
"O sistema deve calcular o adicional noturno.""O sistema deve estar disponível 99,5% do tempo no mês."
Truque para a provaPergunte: "Isso é uma ação ou função que o usuário pode pedir ao sistema?" Se sim, é RF. Se a frase fala de velocidade, segurança, disponibilidade, usabilidade, compatibilidade, lei, padrão, linguagem de programação, tecnologia, é RNF.

Dois detalhes que costumam cair:

  • RNF frequentemente são mais críticos que RF isolados: se um sistema de aviação não for confiável, ele é inútil, mesmo que tenha todas as funções. Um RNF não atendido pode inutilizar o sistema inteiro.
  • Um RNF pode gerar requisitos funcionais. O RNF "somente usuários autorizados podem acessar os dados" dá origem aos RF de login, cadastro de perfis e controle de permissões.

4.1 Classificação dos RNF (Sommerville)

GrupoOrigemSubtipos e exemplos
Requisitos de produtoComportamento do software em execuçãoEficiência (desempenho e espaço), confiabilidade, proteção (security), usabilidade, dependabilidade. Ex.: "responder em até 2 s"
Requisitos organizacionaisPolíticas e procedimentos da organização do cliente e do desenvolvedorAmbientais, operacionais, de desenvolvimento. Ex.: "deve ser feito em C#/.NET", "deve usar o login único do órgão", "o processo deve seguir o padrão interno de documentação"
Requisitos externosFatores de fora do sistema e do processoRegulatórios, legais (contábeis, de proteção/safety), éticos. Ex.: "deve cumprir a LGPD", "deve seguir a norma do Banco Central"

Há ainda os requisitos de domínio, que vêm do domínio de aplicação (a área de negócio) e podem ser funcionais ou não funcionais. Ex.: num sistema bancário, "o cálculo de juros deve seguir a fórmula definida pelo Banco Central". O risco é que, por serem óbvios para os especialistas, muitas vezes ninguém os explica.

4.2 RNF bom é RNF mensurável

"O sistema deve ser rápido" é um requisito ruim: não dá para testar. Sommerville propõe métricas para tornar os RNF verificáveis:

PropriedadeMétricas possíveis
VelocidadeTransações processadas por segundo; tempo de resposta a um evento; tempo de atualização da tela
TamanhoMegabytes; espaço em memória
Facilidade de usoTempo de treinamento; número de telas de ajuda
ConfiabilidadeTempo médio entre falhas (MTTF); probabilidade de indisponibilidade; taxa de falhas; disponibilidade
RobustezTempo de reinício após falha; percentual de eventos que causam falha; probabilidade de corromper dados numa falha
PortabilidadePercentual de código dependente da plataforma; número de plataformas suportadas
Ruim → bom"Deve ser rápido" → "95% das consultas devem responder em até 2 segundos com 500 usuários simultâneos."
"Deve ser fácil de usar" → "Um usuário novo deve conseguir abrir um chamado em até 3 minutos, sem treinamento."
"Deve estar sempre no ar" → "Disponibilidade mínima de 99,5% no mês, medida por monitoramento externo."

4.3 Qualidade de software: ISO/IEC 25010

A norma de qualidade de produto (versão de 2011, a mais cobrada em provas) lista 8 características, ótimas para classificar RNF:

CaracterísticaEm uma frase
Adequação funcionalO software faz as funções certas, completas e corretas
Eficiência de desempenhoTempo de resposta, uso de recursos, capacidade
CompatibilidadeConvive e troca informações com outros sistemas (interoperabilidade)
UsabilidadeFácil de aprender, operar, com proteção contra erros do usuário, acessível
ConfiabilidadeMaturidade, disponibilidade, tolerância a falhas, recuperabilidade
SegurançaConfidencialidade, integridade, não repúdio, responsabilização, autenticidade
ManutenibilidadeFácil de modificar, testar, reutilizar e analisar
PortabilidadeFácil de instalar e adaptar a outros ambientes

6. Análise: classificar, priorizar e negociar

Depois de levantar, é preciso organizar: agrupar requisitos relacionados, eliminar duplicados, identificar conflitos e decidir prioridades. Quando dois stakeholders querem coisas incompatíveis, o analista promove a negociação, normalmente avaliando custo, risco e valor de cada pedido. A priorização (por exemplo, pelo método MoSCoW) é vista em detalhe amanhã.

7. Especificação

O resultado é o documento de requisitos, também chamado de SRS (Software Requirements Specification). As normas de referência são a antiga IEEE 830 e a atual ISO/IEC/IEEE 29148. Uma estrutura típica tem: introdução (propósito, escopo, glossário), descrição geral (perspectiva do produto, usuários, restrições, premissas) e requisitos específicos (funcionais e não funcionais).

7.1 Formas de escrever requisitos

  • Linguagem natural: frases livres; fácil de ler, mas ambígua.
  • Linguagem natural estruturada: formulários ou modelos padronizados (identificador, descrição, entradas, saídas, pré e pós-condições).
  • Notações gráficas: diagramas UML (casos de uso, sequência).
  • Especificações matemáticas: precisas, mas difíceis para o cliente entender.

7.2 Características de um bom requisito (IEEE 830)

  • Correto: representa uma necessidade real;
  • Não ambíguo: só uma interpretação possível;
  • Completo: não falta nada importante;
  • Consistente: nenhum requisito contradiz outro;
  • Classificado por importância e estabilidade;
  • Verificável (testável): dá para provar que foi atendido;
  • Modificável: a estrutura do documento permite alterá-lo com facilidade;
  • Rastreável: dá para saber de onde veio e onde foi implementado.
Ambíguo × claro"O sistema deve exibir os processos recentes." (recente quanto?)
→ "O sistema deve exibir os processos cadastrados nos últimos 30 dias, do mais novo para o mais antigo."

"O sistema deve processar os pedidos e/ou enviar e-mail." (e/ou é ambíguo)
→ separe em dois requisitos, cada um com um "deve".

Boas práticas de redação: usar "deve" para obrigatórios e "pode"/"deveria" para desejáveis, de forma consistente; um requisito por frase; evitar jargão técnico em requisitos de usuário; manter um glossário; e destacar as partes-chave.

8. Validação

A validação verifica se o documento descreve o sistema que o cliente realmente quer. É diferente da verificação feita depois, no código.

O que se confere (Sommerville):

  • Validade: os requisitos atendem às necessidades reais? (pode haver necessidades diferentes das imaginadas no início)
  • Consistência: há requisitos conflitantes?
  • Completude: estão todas as funções e restrições?
  • Realismo: é possível implementar com a tecnologia, o prazo e o orçamento disponíveis?
  • Verificabilidade: dá para escrever testes que demonstrem o atendimento?

Técnicas: revisões de requisitos (análise sistemática por uma equipe, inclusive inspeções formais), prototipação (mostrar um modelo executável aos usuários) e geração de casos de teste (se não dá para escrever um teste, o requisito está mal escrito).

Verificação × validação (Boehm)Validação: "Estamos construindo o produto certo?" (atende ao que o cliente precisa?)
Verificação: "Estamos construindo o produto do jeito certo?" (está de acordo com a especificação?)

Mapa-resumo

  • Processo: levantamento → análise → especificação → validação, de forma iterativa, com gerenciamento ao lado.
  • RF = o que faz. RNF = como deve ser (qualidade e restrição), de produto, organizacional ou externo.
  • RNF precisa ser mensurável.
  • Técnica certa para cada problema: observação para o que ninguém fala; JAD para consenso; protótipo para incerteza; engenharia reversa para legado.
  • Bom requisito: não ambíguo, completo, consistente, verificável, rastreável.
Não esqueçaPressman: concepção, levantamento, elaboração, negociação, especificação, validação, gestão. Métricas de RNF: velocidade (tempo de resposta), confiabilidade (MTTF, disponibilidade), usabilidade (tempo de treinamento), portabilidade (% de código dependente da plataforma).

Exercícios de fixação

Questões inéditas no estilo FGV, escritas para esta apostila.

Questão 1 · inédita

Em entrevista, a chefe do almoxarifado pediu: (1) cadastrar entradas de material; (2) "que a tela abra rápido, em menos de 2 segundos"; (3) emitir relatório mensal de consumo por setor; (4) "que funcione no celular dos conferentes"; (5) alertar quando o estoque ficar abaixo do mínimo. A quantidade de requisitos funcionais e não funcionais é, respectivamente,

  1. 2 e 3.
  2. 3 e 2.
  3. 4 e 1.
  4. 5 e 0.
  5. 1 e 4.
Ver gabarito comentado

Gabarito: B. Funcionais: cadastrar entradas (1), emitir relatório (3), alertar estoque mínimo (5). Não funcionais: desempenho (2) e compatibilidade/portabilidade (4).

Questão 2 · inédita

Uma equipe precisa substituir um sistema de folha de pagamento de 1998, sem documentação e cujos desenvolvedores já saíram do órgão. A técnica de levantamento mais adequada como ponto de partida é

  1. o brainstorming com os novos estagiários.
  2. o questionário enviado a todos os servidores.
  3. a engenharia reversa do sistema legado (código, banco de dados e telas).
  4. a prototipação descartável de novas telas.
  5. a especificação direta de casos de teste.
Ver gabarito comentado

Gabarito: C. Quando o conhecimento das regras está "preso" no sistema antigo, a engenharia reversa é a forma de recuperar os requisitos. As outras técnicas podem complementar depois.

Questão 3 · inédita

O requisito "O sistema deve estar em conformidade com a Lei Geral de Proteção de Dados" é classificado, segundo Sommerville, como requisito

  1. funcional de usuário.
  2. não funcional de produto.
  3. não funcional organizacional.
  4. não funcional externo.
  5. de domínio funcional.
Ver gabarito comentado

Gabarito: D. Requisitos legais e regulatórios vêm de fora da organização: são não funcionais externos.

Questão 4 · inédita

Assinale a opção que apresenta um requisito não funcional adequadamente especificado.

  1. O sistema deve ser intuitivo.
  2. O sistema deve ter ótimo desempenho.
  3. O sistema deve suportar 1.000 acessos simultâneos com tempo de resposta de até 3 segundos em 95% das requisições.
  4. O sistema deve permitir a emissão de boletos.
  5. O sistema deve ser seguro contra qualquer ataque.
Ver gabarito comentado

Gabarito: C. É o único mensurável e verificável. A, B e E são vagos; D é um requisito funcional.

Questão 5 · inédita

Os servidores de um setor sempre esquecem de mencionar, nas entrevistas, um controle paralelo que fazem numa planilha. A técnica mais indicada para revelar esse tipo de requisito implícito é

  1. a observação do trabalho (etnografia).
  2. a entrevista fechada.
  3. a análise de pontos de função.
  4. o modelo em V.
  5. a revisão por pares do código.
Ver gabarito comentado

Gabarito: A. Observando a rotina real, o analista vê o que as pessoas fazem e não lembram de contar.

Questão 6 · inédita

Durante a validação de requisitos, a equipe tentou escrever casos de teste para cada requisito e não conseguiu fazê-lo para "o sistema deve ser amigável". Isso indica que o requisito não atende principalmente à característica de

  1. rastreabilidade.
  2. verificabilidade.
  3. consistência.
  4. priorização.
  5. modularidade.
Ver gabarito comentado

Gabarito: B. Se não é possível testar, o requisito não é verificável. A geração de casos de teste é justamente uma técnica de validação.

Questão 7 · inédita

A pergunta "Estamos construindo o produto certo?" está associada à

  1. verificação.
  2. validação.
  3. implantação.
  4. manutenção adaptativa.
  5. gerência de configuração.
Ver gabarito comentado

Gabarito: B. Validação confere se o produto atende às necessidades reais do cliente. Verificação confere se o produto está de acordo com a especificação.

Questão 8 · inédita

Duas diretorias apresentam necessidades conflitantes para o mesmo módulo de um sistema. Para obter consenso rápido entre elas, com participação conjunta de usuários e equipe de TI, é mais indicado usar

  1. questionário anônimo.
  2. análise de documentos.
  3. workshop no formato JAD.
  4. engenharia reversa.
  5. observação passiva.
Ver gabarito comentado

Gabarito: C. O JAD (Joint Application Design) reúne todos numa sessão facilitada, ideal para negociar e fechar decisões.

Questão 9 · inédita

Segundo Pressman, a tarefa da engenharia de requisitos em que se conciliam conflitos entre os interessados e se priorizam os requisitos, considerando custo e risco, é a

  1. concepção.
  2. elaboração.
  3. negociação.
  4. especificação.
  5. gestão.
Ver gabarito comentado

Gabarito: C. Na negociação, o analista ajuda os interessados a resolver conflitos e decidir prioridades. A elaboração refina os requisitos em modelos; a gestão controla as mudanças.

Questão 10 · inédita

Para tornar verificável um requisito de confiabilidade, a métrica mais adequada é

  1. número de transações processadas por segundo.
  2. tempo médio entre falhas (MTTF).
  3. tempo necessário para treinar um usuário novo.
  4. percentual de código dependente da plataforma.
  5. tamanho do sistema em megabytes.
Ver gabarito comentado

Gabarito: B. MTTF, disponibilidade e taxa de falhas medem confiabilidade. A mede velocidade; C, facilidade de uso; D, portabilidade; E, tamanho.
